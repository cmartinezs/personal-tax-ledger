Distribución desktop

Windows validado; Linux es el próximo target

La ruta Windows está cerrada funcionalmente con un instalador autocontenido. El packaging parte desde un staging mínimo y reproducible; Linux reutilizará esa base, pero todavía no está implementado ni certificado.

Pipeline Windows actual

flowchart TD R["Monorepo"] --> B["npm run build"] B --> T["build-desktop-runtime.mjs"] T --> D[".desktop-runtime"] D --> M["paquetes internos físicos"] M --> P["@electron/packager"] P --> A["resources/app.asar / win32-x64"] A --> Z["materializar 7z.exe + 7z.dll"] Z --> S["electron-winstaller / Squirrel.Windows"] S --> X["PersonalTaxLedger-Setup.exe"]

Por qué existe el staging

El artefacto desktop no se construye copiando el monorepo tal cual. scripts/build-desktop-runtime.mjs crea un runtime autocontenido, materializa físicamente los paquetes internos y excluye tests, documentación, scripts de desarrollo y otros archivos que no pertenecen al runtime.

Esta decisión evita depender de symlinks de npm workspaces generados en WSL/Linux, que no produjeron un árbol portable válido para Windows.

Construcción del instalador desde WSL

El instalador Windows fue generado desde WSL2/Ubuntu. El host de build requiere Mono, Wine 64-bit y soporte i386/WoW64 cuando Squirrel ejecuta helpers Windows que lo necesitan. Esas dependencias pertenecen al host de build, no al PC del usuario final.

npm run desktop:check
npm run desktop:package:win
npm run desktop:installer:win

Salida final:

out/installer-win32-x64/PersonalTaxLedger-Setup.exe

ASAR y pruning

ASAR habilitado

asar:true fue validado en Windows y reduce el file sprawl del runtime. No se considera cifrado ni control de seguridad.

VALIDADO

Packager prune deshabilitado

prune:true eliminó paquetes internos materializados y provocó ERR_MODULE_NOT_FOUND. El pruning genérico queda rechazado.

RECHAZADO

7-Zip de Squirrel

electron-winstaller@5.4.4 distribuye helpers por arquitectura, mientras Squirrel esperaba aliases genéricos 7z.exe y 7z.dll. PTL los materializa explícitamente en scripts/create-windows-installer.mjs usando os.arch() antes de invocar el instalador.

El clean install final demostró que el lifecycle script de electron-winstaller puede permanecer bloqueado y el build continúa siendo reproducible gracias a este preflight propio.

Datos y lifecycle

La SQLite desktop vive bajo app.getPath('userData')/data/personal-tax-ledger.sqlite, fuera del directorio de instalación. Se validó continuidad de datos en cierre/reapertura, instalación sobre instalación existente y desinstalación/reinstalación.

flowchart LR SETUP["Setup.exe"] --> BIN["Binarios instalados"] APP["Aplicación"] --> DATA[("Electron userData / SQLite")] BIN --> APP RE["reinstall / install-over"] --> BIN UN["uninstall + reinstall"] --> BIN DATA --> APP

Próximo target: Linux

Linux debe reutilizar el mismo apps/local, core y staging autocontenido. Sin embargo, todavía falta decidir y validar el empaquetado nativo, formato de distribución, integración con desktop entries, iconografía, lifecycle, path real de userData y pruebas en una distribución objetivo.

flowchart TD COMMON["core + application + apps/local + staging"] --> WIN["Windows x64"] WIN --> WSTAT["PASS"] COMMON -. "próximo slice" .-> LIN["Linux"] LIN --> LP["elegir package format"] LP --> LU["UAT nativo + persistencia + lifecycle"]
No se marca Linux como soportado todavía. La arquitectura es compatible con avanzar hacia ese target, pero el soporte sólo se declarará después de construir y validar un artefacto nativo real.
